# MEMORY.md — 老照片修复工作台

## 长期上下文
- 项目起点：用户 @ 了一个叫「AI绘图」的技能要求修复老照片，但**该技能在本机并不存在**（用户级技能目录无此技能，技能市场也无同名条目）。
- 用户附带的参考文件（`cnb-old-photo-restoration` 社区案例）暴露了原始实现：技能 `image-beautify` + `scripts/beautify.py`，本地 OpenCV 管线。该技能同样未安装。
- **用户随后明确了真实需求**：不要一次性交付，要一个**可操作的页面版**，今后自己指定输入输出路径。这改变了整个解法——从"跑一次脚本"变成"做一个能长期用的工具"。
- 因此本项目 = 单文件浏览器端工作台（主产物）+ Python CLI 参考实现（批量路径）。

## 架构决策
- **决策**：页面做成单文件、零依赖、零外链，算法全部自实现。
  - 原因：① 仓库根 AGENTS.md 的既有约定就是单文件零依赖；② 照片涉隐私，不上传；③ 离线可用；④ 引入 OpenCV.js 需从 CDN 拉 ~9MB WASM，国内网络下脆弱，且违反"不引入一个解决小问题却带来十个新问题的依赖"。
  - 影响：去噪算法从 NLM 换成导向滤波（见下）；换来了秒级启动与完全可控的参数。
- **决策**：去噪用 YCbCr 分离的自导向滤波，而非 RGB 逐通道。
  - 原因：亮度通道温和、色度通道 3 倍强度，是专业修图通行做法；实测三项指标同优（平区降噪 74.9% vs 71.5%、纹理保留 0.968 vs 0.950、饱和度 107.8 vs 102.8）。
  - 影响：多两次色彩空间转换，可忽略。
- **决策**：亮度用 gamma 提亮、对比度用 smoothstep S 曲线、饱和度用 luma 保持式混合。
  - 原因：三者都是为了消除具体的量化缺陷——线性提亮裁剪率 35%、线性对比度把 >233 的像素并到 255、HSV 抬高 S 会拉低暖色亮度约 9 个灰阶。
  - 影响：与 Python 版语义不同（Python 版已同步改成一致），文档中列了对照表。
- **决策**：指标从"前后两点"改为"逐阶段五点"。
  - 原因：单看最终值会误导——锐化必然抬高高频，导致"噪声 σ 上升"看起来像去噪失败，实际是锐化的正常代价。
  - 影响：`state.stages` 保存每个阶段的全套指标，说明文档直接引用。

## 踩坑记录
- **现象（严重）**：去噪后 `warm_bias`（R−B 均值差）从 64.7 精确变为 **0**，饱和度 111.75 → 27.39，画面色彩整体崩坏。
  - 根因：`stepDenoise` 用 `out.set(channel, c*N)` 写入的是**平面（planar）布局**，而管线其余部分按**交错（interleaved）`rgb[i*3+c]`** 读取。三通道被错位解释。
  - 解决：改为 `out[i*3+c] = filtered[i]`。**回归项已加入验收脚本**（"去噪：暖偏未被错乱"）。
  - 教训：颜色通道布局是最容易静默出错的地方，且不会抛异常。用"通道间均值差"这类指标能立刻暴露它。
- **现象**：`eps=787` 时局部方差中位数 322 → 自适应系数 `a` 中位数仅 0.29，典型像素 71% 被替换成局部均值，纹理被抹平。
  - 根因：eps 是我凭"0.11×255 的平方"拍出来的，没有实测标定。
  - 解决：做参数扫描，按"平区降噪 vs 纹理保留"的权衡曲线定标为 light(2,50,150) / medium(3,120,360) / strong(4,300,900)。
  - 教训：滤波器的 eps **必须实测定标**，不能套用教科书的影像尺度公式。
- **现象**：线性亮度 `out = 1.2·src + 19.2` 导致 **34.75%** 的通道值被压到 0/255。
  - 根因：加性偏移对全图等量抬升，亮部必然越界。
  - 解决：改用 gamma 提亮（暗部抬升大于亮部，天然保护高光）+ smoothstep S 曲线（值域严格 [0,1]）。裁剪率回到 +2.1 个百分点。
- **现象**：Python 版饱和度增强后平均亮度反而下降 9 个灰阶（159.2 → 150.3）。
  - 根因：HSV 中保持 V（最大通道）不变而抬高 S，等于压低最小通道；暖色像素的 B 被压低，加权亮度随之下降。
  - 解决：改用 luma 保持式 `Y + (C−Y)×sat`，按定义不改变 Y。
- **现象**：缩放后的图片 `flat_noise` 全部返回 `null`（平坦区掩膜为空）。
  - 根因：512 桶直方图求分位数，每桶代表 8 个灰阶²；当 25 分位落在第 0 桶时阈值算成 0，`v < 0` 永不成立。
  - 解决：改用 4096 桶（1 灰阶²／桶）。
- **现象（方法论缺陷）**：更早的掩膜口径是"局部方差 25 分位以下"，但完全裁剪成纯白/纯黑的过曝区域方差恒为 0，会被判为"平坦区"——那里本来没有噪声，混进来把噪声测量值稀释成无意义的 0。
  - 解决：改用 **10–40 分位带**，同时排除底部退化区与顶部纹理区。
- **现象**：`buildMarkdown` 整个函数未定义，页面所有按钮失效。
  - 根因：模板字符串里写了 Markdown 行内代码标记（反引号），未转义，把模板字符串提前终止。
  - 解决：转义为 `\``。**排查手法**：抽取 `<script>` 块 → `node --check`，比在浏览器里看报错快得多。
- **现象**：验收脚本判"锐化失败：清晰度未超过原图"（1188.9 → 1103.3）。
  - 根因：判定口径错了，不是代码错。原图带重颗粒，整图 Laplacian 方差被颗粒抬高；去噪必然降低它，且不该、也无法"恢复到颗粒级别的高频"。
  - 解决：改为比较"锐化前 → 锐化后"（843 → 1103，+30.8%），并新增「纹理保留」指标直接度量塑料感。
- **现象**：`chrome --screenshot` 验证不了这个页面。
  - 根因：该命令只截视口，且不执行页面脚本、读不到运行时状态；本页面的核心逻辑全在运行时。
  - 解决：`tools/verify_page.js` 用 CDP 驱动，`Emulation.setDeviceMetricsOverride` + `DOM.setFileInputFiles` + `Runtime.evaluate(awaitPromise)`。仓库根 MEMORY.md 早有同类记录。
- **环境**：管理的 python 3.13 与 `envs/default` 都缺 cv2。
  - 解决：向隔离 venv 装 `opencv-python-headless` + `numpy`（腾讯云 pypi 镜像）。严禁污染系统全局环境。

## 用户纠正 / 偏好
- **明确要求"页面版"**，要能自己指定输入输出路径反复使用——不要一次性产物。
- 输出必须 **PNG 无损**，不得用 JPG 有损压缩交付。
- 色彩增强"追求自然，不要过饱和"——默认饱和度系数 1.4 是上限，不轻易上调。
- 面部区域优先保护，去噪不得导致"塑料感"——这条直接催生了「纹理保留」指标与面部保护开关。
- 会附带参考文件（前次产出 + 说明文档），说明其习惯是**以已有产出为标准做对齐**，应先读参考再动手。
- 我犯过一个操作错误：把已劣化的测试图当源图又劣化了一次（双重颗粒）。生成测试素材时必须用**干净的原图**作为输入。
